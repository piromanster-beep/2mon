API 2mon

Базовый URL в примерах — https://ваш-домен.ru. Формат обмена — JSON, UTF-8.

Все эндпоинты:

  POST /wh/{token}            — вебхук от систем мониторинга
  POST /bot                   — вебхук от MAX (обновления бота)
  GET  /healthz               — проверка живости
  GET  /admin                 — страница входа в админку
  POST /admin/login           — вход в админку
  GET  /admin/dashboard       — список пользователей
  POST /admin/ban/{chatID}    — блокировка/разблокировка
  POST /admin/limit/{chatID}  — изменение дневного лимита

--------------------------------------------------------------------------------
ВЕБХУК ДЛЯ СИСТЕМ МОНИТОРИНГА
--------------------------------------------------------------------------------

POST /wh/{token}

{token} — токен пользователя, выданный ботом (команда /token).

Заголовки:
  Content-Type: application/json

Тело запроса:
  {
    "subject": "Тема сообщения",
    "message": "Текст сообщения",
    "severity": "critical|warning|info"
  }

Ответы:
  200 {"status":"queued"}          — сообщение принято в очередь
  200 {"status":"heartbeat_ok"}    — heartbeat принят (subject=heartbeat)
  400 "bad request"                — тело запроса не является JSON
  403 "user disabled"              — пользователь заблокирован
  404 "invalid token"              — токен не найден
  429 "daily limit exceeded"       — дневной лимит превышен
  429 "queue full"                 — очередь отправки переполнена
  500 "internal error"             — сбой БД или очереди

Heartbeat:
  Если subject равен "heartbeat" (без учёта регистра), сообщение НЕ тратит
  дневной лимит и не логируется — обновляется только last_heartbeat.
  Если до этого пользователю уже отправляли уведомление об обрыве
  (heartbeat_alert_sent), в ответ на восстановление ему уходит сообщение
  "Heartbeat восстановлен".

Оформление текста в MAX (severity влияет на эмодзи):
  critical, high, disaster   -> 🔴
  warning, average           -> ⚠️
  information, info          -> ℹ️
  прочее                     -> ℹ️
  subject с префиксом "Resolved" -> ✅ (зелёная галочка, шаблон "✅ *subject*\nmessage")

  Итоговый текст: "<эмодзи> *<subject>*\n<message>"

Куда доставляется:
  Если у пользователя привязана группа (group_chat_id), сообщение идёт в
  группу, иначе — в личный чат с ботом.

Если формат вашей системы мониторинга отличается, добавьте адаптер в
internal/handler/webhook.go (см. DEVELOPMENT.md).

ВЕБХУК ДЛЯ MAX (БОТ)
--------------------------------------------------------------------------------

POST /bot

Принимает обновления от MAX. Формат запроса — JSON согласно MAX Bot API.
Настраивается через API MAX:

  curl -X POST "https://platform-api.max.ru/subscriptions" \
    -H "Authorization: ТОКЕН_БОТА" \
    -H "Content-Type: application/json" \
    -d '{"url":"https://ваш-домен.ru/bot","update_types":["message_created","bot_started"]}'

Поддерживаемые update_type:
  message_created  — текстовое сообщение (обрабатываются команды)
  bot_added        — бота добавили в диалог/группу

Команды бота (личный чат):
  /start            — регистрация, получение токена
  /token            — показать текущий токен
  /newtoken         — предупреждение о смене токена (токен не меняется)
  /newtoken confirm — подтвердить смену: старый токен перестаёт работать
  /status           — статистика за сегодня
  /heartbeat        — статус heartbeat
  /bind ID | /bind off — привязать/отвязать группу (выполняется в личке)
  /help             — справка

Команды бота (группа; бот должен быть администратором группы):
  /start            — регистрация группы, подсказка про /bind
  /status, /heartbeat, /groupid, /help
  Токен в группе не показывается; на обычные сообщения бот не реагирует.

Подсказки команд для клиента MAX регистрируются автоматически при старте
сервиса (PATCH /me/commands). Если запрос не удался — в логах будет строка
вида "[commands] ...", команды при этом продолжают работать.

Дневной лимит (daily_limit) считается по записям messages_log за текущую дату
и сбрасывается в полночь по времени сервера.

GET /healthz

Ответ:
  200 {"status":"ok"}

MongoDB в этой проверке намеренно не пингуется: endpoint отражает только
доступность HTTP-сервиса и удобен для Docker/оркестратора.

--------------------------------------------------------------------------------
АДМИНКА
--------------------------------------------------------------------------------

GET  /admin                  — страница входа
POST /admin/login            — вход (form-поле password)
GET  /admin/dashboard        — список пользователей
POST /admin/ban/{chatID}     — переключить блокировку пользователя
POST /admin/limit/{chatID}   — задать дневной лимит пользователя

Сессия: после входа ставится кука admin_session (HttpOnly, SameSite, Path=/admin),
в качестве значения используется SHA-256 от строки "2mon-admin-session:" + пароль (не сам пароль). Первого
администратора создают вручную в MongoDB: db.users.updateOne({chat_id:"..."},
{$set:{is_admin:true}}).

--------------------------------------------------------------------------------
HEARTBEAT (МОНИТОРИНГ СИСТЕМЫ МОНИТОРИНГА)
--------------------------------------------------------------------------------

Назначение — следить, что со стороны Zabbix (или другой системы) всё живо.

  Система отправляет вебхук с subject=heartbeat каждые 5 минут
  2mon обновляет last_heartbeat
  Scheduler раз в минуту проверяет просроченные heartbeat
  Если heartbeat молчит больше 15 минут:
    — администратору: уведомление в MAX (с ChatID пользователя)
    — пользователю: уведомление в MAX ("Ваш Zabbix не отправляет heartbeat")
  При восстановлении heartbeat (если ранее слали alert):
    — пользователю: "✅ Heartbeat восстановлен. Ваш Zabbix снова на связи."

Пример heartbeat-запроса:

  curl -X POST https://ваш-домен.ru/wh/TOKEN \
    -H "Content-Type: application/json" \
    -d '{"subject":"heartbeat"}'
